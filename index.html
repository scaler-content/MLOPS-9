CI/CD · GitHub Actions · Amazon ECS — Part 1 of 2

Teaching a pipeline to test, build, and deploy a service by itself

A service that changes every week needs releases nobody has to remember the steps for. This is how a GitHub Actions pipeline checks every change with CI, and ships the changes that pass with CD — without a single long-lived password sitting in GitHub.

~35–40 min read Part 1 of 2 — staging & rollback in Part 2 MLOps · Docker · ECS prerequisite
Why this exists

One deployment by hand is fine. The tenth is not.

A service that only changes once can be shipped once, carefully, by a person clicking through a console. A real service doesn't work that way — it changes every week, and every change needs the same care the first one got: checked, built, pushed, and released correctly, every single time.

Done by hand, that care erodes fast. A test step gets skipped because the change "looks harmless." A tag gets typed wrong. A step to point the service at the new version gets forgotten, so the old one keeps quietly running. Someone builds from a laptop with uncommitted changes, so the image that ships matches no commit at all. A month later, when something starts behaving oddly, nobody can say for certain which code is actually live.

The fix is to hand the repeatable part to a program that does it the same way every time — a pipeline. This post walks through building one with GitHub Actions: first the checking half, then the releasing half, then — because pipelines fail in their own particular ways — a tour of exactly how this one breaks, including a failure mode where every test passes, the run is green, and the change never actually reaches users.

What you'll be able to do after this
  • Explain CI, continuous delivery and continuous deployment — and say which ones a given pipeline actually does.
  • Read any GitHub Actions workflow and name its trigger, job, runner, steps and actions.
  • Run a service's tests on every pull request and publish the results where reviewers already look.
  • Push a commit-tagged image to a private registry with immutable tags, and explain why that matters.
  • Let GitHub Actions into AWS with OIDC — no access keys, no stored secrets, one-hour credentials.
  • Diagnose common pipeline failures from logs and AWS — including the one that reports success and isn't.

Assumes you can already write and run pytest tests, have built a FastAPI service with Docker, and have stood up that service on Amazon ECS — this picks up right where that leaves off.

01 — Foundations

What a pipeline actually does

Picture the week after a model gets retrained and the new version is better. Getting it safely in front of users takes seven steps, done faithfully, every time:

Step 1 of 7 — Continuous Integration

Check that the change works

Run the test suite against the new code, before it goes anywhere near production. This is the step that's easiest to skip under pressure — and the one that's skipped right before something breaks.

Each step is simple in isolation. The trouble starts when a person does all seven by hand, several times a week: step 1 gets skipped because the change "looks harmless," a tag gets mistyped, step 6 gets forgotten and the old version keeps serving traffic. A pipeline runs the same seven steps the same way every time, starting itself whenever the repository changes.

Two names, two halves

Step 1, automated

Continuous Integration (CI)

Every change pushed to the shared repository is built and tested immediately — before it merges into main. Breakage is caught within minutes, not weeks later when someone tries to ship it.

Steps 2–7, automated

Continuous Delivery / Deployment (CD)

Delivery: every change that passes CI ends up ready to release (here, an image in a registry) — a person still presses the button. Deployment goes one step further and presses that button automatically too.

Why the order matters

This pipeline does both halves, strictly in that order: tests run on every pull request and every push to main; only when they pass on main does the same pipeline deploy, all the way to the live service. CD without CI just ships broken code faster.

Many tools run pipelines — Jenkins, GitLab CI/CD, CircleCI each have their own file format. This uses GitHub Actions because the code already lives on GitHub and the pipeline becomes one more file in the same repository. The ideas carry over regardless of tool; only the syntax changes.

One constraint shapes everything that follows: a pipeline can only type commands — it can't click through a console. So every release step below is first run by hand from a terminal, and only then handed, verbatim, to GitHub Actions.

02 — The subject

The service under test

The pipeline deploys a small pump-health prediction service — the same FastAPI app from earlier sessions, built with Docker and already running once on Amazon ECS. It has one addition that turns out to matter a great deal: /health now also reports git_sha, the exact commit its running image was built from.

The Dockerfile takes the commit hash as a build argument, and the app reads it back out of an environment variable at startup. With that one field, a single HTTP request answers a question that's surprisingly hard to answer by hand: which version of the code is actually live, right now? Every verification step in the rest of this post leans on it.

03 — Vocabulary

GitHub Actions, in five words

A pipeline needs something to start it and a machine to run on; with GitHub Actions, both come from GitHub itself. Everything it needs to know lives in a YAML file inside the repository — so the pipeline is versioned, reviewed and rolled back exactly like any other code.

Here's a minimal first workflow that tests and deploys nothing — it only looks around the machine it runs on. Click each term on the left to see which lines it names.

What the runner reports back

Pushing this file starts a run within seconds. Opening its one step prints three things worth noticing:

x86_64 architecture

GitHub's standard runners are Intel machines, so an image built there is amd64 with no --platform flag needed — the architecture trap from building on Apple silicon simply can't happen here.

Docker & the AWS CLI, pre-installed

A GitHub-hosted runner ships with a long list of tools already on it, so the release steps built later in this post run on it exactly as typed.

The repo is already there

ls lists the project files — that's the checkout step's doing. Skip it, and the runner is an empty machine that knows nothing about the code.

The whole job takes about eight seconds, then the machine is deleted. Every run starts from nothing — exactly what you want from a check or a release, since nothing can ever depend on a file somebody once left behind on the build machine.

04 — Continuous Integration

Tests on every pull request

A change should be checked before it joins main, not after. On GitHub, the place a change waits before joining main is a pull request — so that's where CI runs. Every time one is opened or gets a new commit, the tests run and the result appears right where the reviewer is already looking.

The tests

FastAPI's TestClient runs the app in-process and sends it requests — no server, no container, no AWS account needed. Four tests check the essentials: /health reports ok, /predict returns a probability with the right threshold, a worn pump scores higher than a healthy one, and an impossible sensor reading gets rejected outright.

The workflow that runs them

The same commands, handed to a runner. This file is called pipeline.yml because the deploy job joins it later in the same file.

pull_request fires whenever one opens or gets a new commit. push to main fires after every merge, checking the merged result once more. workflow_dispatch just adds a manual "Run workflow" button for ad-hoc runs.

The top-level block gives every job's token read-only access to the code and nothing else. The test job asks for two things on top: checks: write to post its own check, and pull-requests: write to comment. Each job requests only what it personally needs — the deploy job later asks for something else entirely, and never for this.

It writes results to JUnit XML, a format almost every CI tool understands regardless of the tests' own language. A publishing action reads that file and turns it into both a check on the commit and a running comment on the pull request — the reviewer never has to open the Actions tab. Reading a results file is sturdier than scraping pytest's printed output: the action knows exactly which test failed and why, without parsing text.

if: ${{ !cancelled() }} keeps it running even after an earlier step fails — a failing report is exactly the one the reviewer needs to see. The job itself still shows red, because the test step failed; only the reporting step is exempted from being skipped.

What a reviewer actually sees

Push a branch

Starts nothing yet — the workflow only triggers on pull requests and pushes to main.

Open the PR

Both triggers fire. Checks appear in the PR's status box within seconds.

Checks turn green

~45s later: the job itself, and a second check added by the publish action.

A bot comments

Counts, pass/fail, and which commit was tested — updated in place on every push, never duplicated.

Merge

A push to main. The pipeline reruns on the merged code — no new comment, since there's no open PR to post it on.

Case study — a renamed file nobody committed

Someone renames the model file on their laptop, updates the code to load the new name — and forgets to commit the renamed file itself. Within 45 seconds of opening the PR, both checks turn red, and the comment compares the branch against main: 4 tests, 0 passed, 4 errors. All four are errors, not failures — the fixture that loads the model broke before a single test could even start.

FileNotFoundError: [Errno 2] No such file or directory: 'model/pump_model.joblib' raised in the fixture at tests/test_app.py:23

The reviewer knows exactly what's wrong, without running anything, less than a minute after the push. Without these tests, this exact bug would only have surfaced after being built and deployed. Nothing here is blocking the Merge button yet, though — that's a branch-protection setting, covered in Part 2. For now, the rule is only as good as the people following it.

05 — Continuous Delivery, prepared

A registry, the standing infrastructure, and one release by hand

The CD half starts in a terminal, not a console — because a pipeline can only ever type commands. Everything that doesn't change between releases (the network, load balancer, cluster, log group) gets rebuilt once via the CLI rather than console forms, in the same order and under the same names as before. The service itself — the one thing that does change every release — waits until there's an image for it to run.

Why the image moves to Amazon ECR

Up to now the image has lived on Docker Hub, in a public repository. For a pipeline, it moves to Amazon ECR, AWS's own registry, for three concrete reasons:

01

Private by default

Only identities in the account that are explicitly allowed to can pull from it — a model trained on company data rarely belongs somewhere public.

02

Permissions already exist

The ECS task execution role already carries the managed policy that lets it pull from ECR. Nothing extra to configure, no separate registry token to protect.

03

Same region, no limits

Pulled from right next to the service — no Docker Hub pull limits, no trip across the public internet.

Immutable tags

The ECR repository is created with immutable tags: once a tag is pushed, it can never be moved to point at a different image, and a second push of the same tag is flatly refused. That's what makes a tag trustworthy — if the tag is the Git commit, the image behind it is that commit's image, forever. (This rule resurfaces, sharply, in the failures section below.)

Docker logs in with a temporary token requested from AWS — ECR has no password of its own — and then the release is three familiar commands: build for amd64, tag the image with the full commit hash, push.

The architecture this release stands up

Everything inside the gold boundary already existed before this release — the runner only ever pushes an image and updates one service.

Verifying a release actually happened

The last step registers a new task definition revision pointing at the fresh image, and updates the service to use it — with one new setting switched on: the deployment circuit breaker. During a rollout, ECS counts new tasks that fail to start or fail their health check; past a threshold it stops the deployment, marks it failed, and — with rollback=true — reverts to the last revision that worked. It comes up again, decisively, in the failures section.

Once the service is stable, one request settles the question that matters: curl $ALB_DNS/health returns a git_sha that should match git rev-parse HEAD exactly. If it does, the service is running precisely the commit on screen — and anyone can check that with a single request, any time.

That was one release by hand: a build, a push, a hand-written task definition, a registration, an update — each typed with exactly the right tag. The next release needs all of it again. Nothing in those steps actually needs a person; they need the commit hash, valid credentials, and a machine with Docker and the AWS CLI. The runner already has the tools. What it's missing is credentials.

06 — Trust, without a secret

Letting GitHub into AWS without a key

On a laptop, the CLI uses a personal sign-in. The runner is a fresh machine GitHub owns, so something has to prove to AWS that it's allowed to deploy. The old answer — an IAM user, a long-lived access key, saved as a GitHub secret — works, which is exactly the problem: the key never expires, works from anywhere on earth, and now lives in a second system that also has to be protected. Leaked, it keeps working until someone notices.

The old way — a stored key

  • An IAM user, with a generated access key
  • Key saved as an encrypted GitHub secret
  • Never expires on its own
  • Works from any machine that has it
  • A leak keeps working until someone revokes it
replaced by

OIDC — a signed, short-lived token

  • No key stored anywhere, ever
  • GitHub signs a fresh token per run
  • AWS trades it for credentials good for one hour
  • Trust is scoped to one repo, one branch
  • Nothing to leak but an ARN — just an address

How the handoff actually works

1
Job requests a token

"I am a job from repository X, on branch main." GitHub signs it, so it can't be forged or altered.

2
Token presented to AWS

The job hands the signed token to AWS and asks to assume one specific IAM role.

3
AWS checks two things

The signature, against GitHub's public keys — and the token's claims, against that role's trust policy.

4
One-hour credentials

Both checks pass → AWS returns credentials that expire on their own in an hour. Nothing long-lived is stored anywhere.

Three pieces, built once per account

Tells the AWS account to accept tokens signed by GitHub at all. Created once per account, pointed at GitHub's signing-key URL, with sts.amazonaws.com as the audience.

Names exactly one repository and branch via the token's subject (sub). GitHub now writes that subject using the owner's and repository's numeric IDs — repo:owner@123/name@456:ref:refs/heads/main — so a repo deleted and recreated under the same name by someone else can never match. The condition also pins aud to sts.amazonaws.com.

Five statements, and nothing more than the deploy steps actually do. If the pipeline were ever tricked into running someone else's commands, the absolute worst it could do is deploy an image to this one service.

StatementGrantsScoped to
LogInToEcrFetch a Docker login tokenEverything — AWS doesn't allow narrowing this one
PushToOneRepositoryUpload image layersOnly the pump-health ECR repo
ReadAndRegisterTaskDefinitionsRead & register task definitionsCan't be narrowed below this action type
UpdateOneServiceUpdate & describe a serviceOnly pump-health in mlops-cluster
HandTheExecutionRoleToEcsiam:PassRoleOnly to ecs-tasks.amazonaws.com, only that one execution role
Secret, not variable

The role's ARN isn't a password — anyone who knows it still needs a token the trust policy accepts. But it does contain the AWS account ID, and GitHub prints every step's inputs at the top of the log. Stored as a plain repository variable, it shows up in full in a public log. Stored as a repository secret, GitHub replaces it with *** wherever it would otherwise appear — and once saved, it can never be read back, only replaced.

07 — Putting it together

The deploy job, after the tests

Everything is now in place: the runner has the tools, the role is ready, GitHub holds the role's ARN. What's left is one more job in pipeline.yml, sitting below test — each of its steps is one of the release steps already typed by hand above.

needs: test

Jobs in one workflow normally run in parallel. This single line is what puts CI before CD — deploy waits for test to finish, and never starts at all if it fails. It shows as skipped, not red.

if: … != 'pull_request'

Keeps deploy out of pull requests entirely. The trust policy would refuse its token anyway, but this skips the job cleanly instead of producing a confusing red run.

id-token: write

Without this single permission there is no OIDC token, and therefore no way into AWS at all. Only the deploy job gets it — the test job, which runs on every pull request, never can.

wait-for-service-stability

Makes the final step keep watching until the new task is actually running and healthy — and fail if it never gets there. What happens without this one line is the centerpiece of the next section.

From here on, a release is a merge. Tests run first; only a green test job lets deploy start; the service ends up running the merge commit GitHub itself created, provably, because /health says so.

08 — Reading failure

What goes wrong

A pipeline that works is only half the story — the other half is knowing exactly how it fails, because the error message is often a long way from the real cause. One of the six scenarios below matters more than the rest: it passes every test, reports success, and still doesn't ship the change.

A permission the workflow forgot

Someone reads that workflows should request as few permissions as possible, and trims the deploy job's block down to just contents: read — removing id-token: write. It sounds careful.

Retry validateCredentials: attempt 1 of 12 failed: Credentials could not be loaded… Retry validateCredentials: reached max retries (12); giving up. ##[error]Credentials could not be loaded, please check your action inputs
What actually happened

With no id-token: write, the job never receives an OIDC token at all — the action has nothing to hand AWS, and falls back to looking for access keys that don't exist.

The fix

Restore id-token: write in the job's permissions: block.

Rule of thumb: "credentials could not be loaded from any providers" in an OIDC workflow → check permissions: first, not the role ARN.

A run from the wrong branch

The workflow is triggered manually from a branch other than main. Tests pass fine — then the deploy job fails, precisely:

Retry AssumeRole: reached max retries (12); giving up. ##[error]Could not assume role with OIDC: Not authorized to perform sts:AssumeRoleWithWebIdentity
What actually happened

The trust policy's subject condition names only main. A token from any other branch, a fork, or a pull request carries a different subject — and AWS correctly refuses it.

How to confirm it

CloudTrail records every AssumeRoleWithWebIdentity attempt, including the token's exact subject. Compare it against the trust policy's sub condition, character by character.

This one isn't a bug — it's the trust policy doing precisely its job. Code that hasn't been reviewed yet cannot deploy, even when its tests are green. (In practice, this same error also shows up when a trust policy was copied from an older tutorial using the short subject form without numeric IDs — worth checking first.)

The flagship failure: a green run that deployed nothing

The first two failures were loud — a red run, noticed immediately. This one is quiet, and it starts with something that looks like harmless tidying.

Two small changes, stacked

1. wait-for-service-stability: true gets deleted from the deploy step — "it's just wasted time." Now the step reports success the instant ECS accepts the update request, before anyone checks whether the new task actually starts.

2. Separately, a .dockerignore copied from another project brings along the line **/*.joblib — quietly excluding the model file from every future build, even though it's still sitting in the Git repository.

Every single step in the run still passes. The tests pass, because they run against the checked-out repository, where the model file is still right there. The build succeeds, because Docker just copies whatever's left after .dockerignore filters the folder. It pushes. The task definition registers. The service accepts the update. Nothing in the pipeline ever confirms the new container actually started.

{"status":"ok", … ,"git_sha":"b7a6a49e36a036da5963ecd76957330af96c2645"} HEAD is 759a4a32b0c0e55d5fa9ded65fe73722dcc8715d

The service answers "ok" — but its git_sha is a commit from a minute earlier, not HEAD. The new image is crashing and being retried in the background while the pipeline has already declared victory.

Minutes later, ECS's circuit breaker finally catches up: it rolls the service back on its own — not to the broken release, but to the last deployment that fully completed. Because nothing ever waited for the in-between release to finish either, that rollback lands two commits behind main. Two green pipeline runs, and nobody was told.

How to diagnose it

Compare live git_sha against git rev-parse HEAD; check the ECS service's event list for "rolling back" / "deployment failed"; inspect stopped tasks and their container logs for the real exit reason.

The real error, once found

FileNotFoundError: /app/model/model.joblib — uvicorn giving up because the file the code asks for was never in the image to begin with.

The fix is two-fold: restore wait-for-service-stability: true, so the deploy step itself turns red — slowly, but honestly — the moment the circuit breaker rolls back. And fix the .dockerignore. The deeper lesson: a green pipeline run is not proof of a successful release, and unit tests check the code in the repository — not what actually ends up packaged inside the image.

Re-running a run that already succeeded

Pressing Re-run jobs on a deploy that already shipped fails immediately at the push step:

tag invalid: The image tag '…' already exists in the 'pump-health' repository and cannot be overwritten because the tag is immutable.
What actually happened

The re-run rebuilds the identical commit and tries to push the identical tag — and immutable tags correctly refuse a second push of the same tag.

The fix

Not a bug — this is the immutable-tag rule working as intended. To re-release the same commit, force a fresh deployment of the existing image instead of re-running the build (aws ecs update-service --force-new-deployment).

A failure that's nobody's fault

A deploy fails at Build and push the image, mid pip install:

ERROR: Could not find a version that satisfies the requirement scipy>=1.10.0 (from scikit-learn) (from versions: none) ERROR: No matching distribution found for scipy>=1.10.0
What actually happened

Nothing is wrong with the code — (from versions: none) means PyPI simply didn't answer the runner at that moment. A brief, ordinary network hiccup.

The fix

Re-run failed jobs — safe here, unlike the scenario above, because this run never got far enough to push an image tag.

Side note: scipy isn't even pinned in requirements.txt — it arrives transitively through scikit-learn, which is exactly why pinning everything, including transitive dependencies, avoids surprises like this one.

A push without a login

From a laptop, an expired Docker login against ECR fails with a deliberately vague message:

push access denied, repository does not exist or may require authorization: authorization failed: no basic auth credentials
What actually happened

The repository does exist — ECR won't confirm which cause applies, to avoid leaking information. In practice it's almost always a stale login; the token behind docker login lasts 12 hours.

The fix

Log in again. The pipeline itself never meets this at all — it authenticates fresh on every single run.

09 — Housekeeping

Tearing it all down

None of this is optional once a session ends. The load balancer, the running task, its public address — all cost money every hour, whether anything is calling them or not. Deletion runs in the reverse order of creation: the service and load balancer first, then task definitions, the cluster, the log group and the ECR repository, then the network, and last — because a role a repository can assume shouldn't outlive its purpose — the OIDC role and identity provider themselves.

The habit worth keeping

Filter every teardown check by the names this session actually created — a shared account can easily hold other people's clusters and load balancers too. The workflow file itself is safe to leave behind: its tests keep running on every pull request, but with the role gone, the deploy job simply can't reach AWS any more.

10 — Looking ahead

Where this fits — and what's still missing

The pipeline now has the right shape: every pull request is tested and reported on, and every merge to main that passes becomes the live service, with no person in between, and anyone can ask the service exactly which commit it's running. Four things a team would still add before trusting it with real users carry over into Part 2.

1

Rules GitHub enforces

A red check doesn't yet block the Merge button, and direct pushes to main are still possible. Branch protection makes the test job a required check.

2

A staging environment

Deploy to a copy first, check the actual running image, only then promote it — exactly what would have caught the .dockerignore bug before it ever reached production.

3

Rollback on purpose

The circuit breaker only helps when tasks fail to start. It can't help when a new model starts fine and simply gives bad answers.

4

Being told

A failed run only matters if someone sees it. Nobody watches a run on main the way a reviewer watches a pull request — notifications close that gap.

11 — The short version

Key takeaways

A pipeline does two things, strictly in order. CI checks every change. CD releases the changes that pass. Releasing itself is six small steps — build, tag, push, register, update, verify — each one just a command, which is exactly what makes it automatable.

Those steps move into a GitHub Actions workflow: an event starts it, jobs run on fresh, disposable runners, and steps either run shell commands or call published actions. The test job runs on every pull request and every push to main, writes JUnit XML, and a publishing action turns that into a check and a live comment exactly where the reviewer is looking. The deploy job carries needs: test, so it only ever starts once tests pass, and it never runs for a pull request at all. Tagging every image with the commit it was built from, inside an immutable-tag registry, ties every running task to exactly one commit — and a git_sha field in /health lets anyone verify it, instantly.

Getting into AWS needs no stored key at all. GitHub signs a token per job; an IAM role trusts that token only for one repository and one branch; its permissions cover pushing to one registry, registering task definitions, updating one service, and handing over exactly one execution role — nothing more.

A green run is not proof of a release. Without wait-for-service-stability, the deploy step finishes the instant ECS accepts the request — and a commit whose tasks crash gets rolled back by the circuit breaker while the pipeline is already reporting success.

And because tests check the code in the repository, not the image that eventually ships, a bug in what actually gets packaged can sail straight through every one of them. Checking the running image itself, before it ever takes real traffic, is where Part 2 picks up.
